KVRN — POST-020 FOLLOW-UP (RECORDED, NOT FIXED)
Recorded during the Final5 freeze-candidate pass per explicit instruction:
"There is a pre-existing checkout issue where some blocked/exhausted/invalid
discount paths may leave an inventory reservation active. Record it as a
post-020 follow-up. Do not fix it inside Final5 unless explicitly instructed
later." This item is OUT OF SCOPE for Final5 and has NOT been touched.

============================================================
BUG: some discount-rejection paths in checkout/session leak the inventory
reservation
============================================================

FILE: lib/checkout-session-handler.ts

The inventory reservation is created once, early, at line 345
(`const reservation = await deps.reserveInventory(items)`), before the
discount-validation block runs. Discount handling then has FOUR return paths,
and only the LAST of them correctly releases what was already reserved:

  1. line 392-394  — validateDiscount() returns invalid
       return NextResponse.json({ error: validation.error }, { status: 400 })
       No deps.failReservation() call. Reservation stays active.

  2. line 403-405  — applyDiscountPriority() returns a blockedReason
       return NextResponse.json({ error: priorityResult.blockedReason }, { status: 400 })
       No deps.failReservation() call. Reservation stays active.

  3. line 433-437  — claimDiscount() returns 'conflict'
       return NextResponse.json({ error: 'Only one discount can be applied per order.' }, { status: 409 })
       No deps.failReservation() call. Reservation stays active. (No discount
       claim was made in this branch, so there is nothing to release there,
       but the earlier inventory reservation is still leaked.)

  4. line 439-444  — claimDiscount() returns 'exhausted'
       return NextResponse.json({ error: 'That code has already been used or is held by another active checkout.' }, { status: 409 })
       No deps.failReservation() call. Reservation stays active.

  Contrast with the branch that DOES do this correctly, immediately below,
  line 452-461 (Stripe coupon unavailable for a merchandise discount):
       try { await releaseDiscountClaim(reservation.reservationId) } catch {}
       try { await deps.failReservation(reservation.reservationId, 'stripe_coupon_unavailable') } catch {}
  That is the pattern the four paths above are missing.

IMPACT
Each of these four rejections is a normal, frequent customer path (a mistyped
or expired code, a code claimed by a concurrent checkout, a shipping/merch
priority conflict) and every one of them currently leaves the reservation row
active until `deps.releaseExpiredReservations()` eventually times it out
(called on a LATER checkout attempt, line 341, not on any schedule tied to
this failure). Until that expiry, the reserved inventory is unavailable to
other customers — a real, if temporary, oversell-prevention cost with no
customer-facing symptom, which is why it has gone unnoticed rather than a
functional-correctness bug.

NOT AN AFFILIATE/COMMISSION ISSUE
This is unrelated to the migration-020 affiliate/referral accounting system
Final5 hardened. It sits entirely in checkout inventory-reservation handling
introduced in earlier migrations (002/003). It is recorded here only because
it was noticed while reading the surrounding checkout code during Final5 and
must not be silently lost.

SUGGESTED FIX SHAPE (not implemented)
Each of the three early returns (1, 2, 4 — case 3 similarly, though it has no
discount claim to release) should mirror the existing line 452-461 pattern:
best-effort release the discount claim if one was taken, then
`deps.failReservation(reservation.reservationId, <reason>)`, before returning
the error response. This should be proven first against the real checkout
route (a reservation row's status after each of the four rejection paths),
per this project's own reproduce-before-fix methodology, not patched blind.


============================================================
RESOLUTION — checkout reservation leak on the four discount-rejection paths
============================================================
STATUS: RESOLVED for the four paths described above. The description above is
preserved unchanged as the historical record.

FIX (lib/checkout-session-handler.ts): one best-effort helper,
failReservationForDiscountRejection(reason, { releaseClaim }), called before
each of the four rejection returns. Status codes and customer-facing messages
are unchanged. Reservation timing, discount economics and inventory accounting
are untouched. No migration was needed.

  invalid code        400  -> failReservation 'discount_code_invalid'
  blockedReason       400  -> failReservation 'discount_blocked'
  claim 'conflict'    409  -> release the claim this reservation already
                              holds, then failReservation 'discount_claim_conflict'
  claim 'exhausted'   409  -> failReservation 'discount_claim_exhausted'
                              (no claim exists for this reservation, so no
                              release is attempted)

Cleanup errors are logged and never replace the customer-facing rejection.

PROOF: nine runtime tests in lib/__tests__/affiliate-http-integration.test.ts
("Post-020 — discount rejections fail the inventory reservation") drive the real
handler against a real PostgreSQL reservation row. Before the fix the four leak
tests failed with reservations.status = 'open' and zero failReservation calls;
after it they pass with status 'failed'. See
CHECKOUT-RESERVATION-LEAK-FIX-EVIDENCE.txt.

SAFETY PASS (follow-up): the exception class above is now RESOLVED too.
validateDiscount() and claimDiscount() are each wrapped; on a throw the handler
fails the reservation (best-effort, errors logged) and returns 503 with
'Could not apply the discount code at this time. Please try again.' - not a 400
invalid-code answer.
  validateDiscount throws  -> failReservation 'discount_validation_error'
  claimDiscount throws     -> release_discount_claim (idempotent; a no-op if no
                              claim was written, releases it if the claim was
                              written but the response was lost), then
                              failReservation 'discount_claim_error'
Real-stock proof: tests S1/S2/E1-E3 use real products, variants, reservation_items
and the real reserve_inventory / release_reservation_by_id SQL; reserved stock
returns to 0 and available to 10. See CHECKOUT-RESERVATION-LEAK-FIX-EVIDENCE.txt
section 9.
